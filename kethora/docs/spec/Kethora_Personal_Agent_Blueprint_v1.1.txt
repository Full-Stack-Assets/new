Kethora Personal Agent
Final product and engineering blueprint
Version 1.1 | 24 September 2026 | Construction specification with G0 decision gates
1. Product contract
Kethora is a persistent personal agent for iOS and the web. A person describes an outcome in ordinary language; Kethora records a task, carries out permitted work on the server, lets the person interrupt or correct it, obtains authenticated approval for consequential actions, and presents a saved result with evidence of what occurred. The person can close one device and continue on another without losing progress.
The initial supported end-to-end task is: inspect user-authorized web pages or uploaded files, create a cited PDF brief, accept a correction, and optionally place a resulting event on a connected calendar after the user approves its exact details. This first path exercises the general platform rather than a separate product. Chat, Feed, Ideas, Goals, Library, activity and Settings share the same identity, permission, task and evidence records. The release plan adds their full behavior in explicit gates; a visible feature cannot be a simulated backend.
Completion definition: an outcome is complete only when its individual acceptance conditions have evidence. A model statement that work happened is neither evidence that a file exists nor proof that an external service accepted a change. A provider timeout after dispatch is unresolved until reconciliation determines the outcome. If evidence is missing, the task says partial or unresolved and explains why.
Document status: this is a build specification. No repository, deployed service, integration, passing test or actual user outcome is asserted by this document. Each later engineering receipt must name the exact commit, environment, real or simulated adapter and evidence used to support a claim.
Build stance: G0 repository, schema and contract work can start now. G1 may build read-to-artifact work while calendar adapters are tested, but G2 cannot enable calendar writes without a per-provider capability result. G1 cannot label a factual brief verified until the citation-judgment and model-quality gates pass. The eight decisions in §22 have accountable roles and due gates; open operational inputs are not silently treated as resolved.

These choices are implementation defaults, not claims about running infrastructure. Public deployment also needs an owned domain, credentials, signing keys, region/account configuration, approved terms and a named incident owner. G0 resolves processor and version pins; G2 requires incident ownership and tested connector access. Those decisions are never delegated to the agent.
Initial safety defaults, versioned in configuration: one-off approval expires after 15 minutes, with an expiring-soon nudge at five minutes remaining; step-up authentication is fresh for five minutes; a dispatch permit lasts at most 60 seconds; an executor lease lasts 30 seconds and renews only while healthy. Hosts synchronize clocks; if measured skew exceeds two seconds or cannot be checked, the gateway refuses a new claim. A first-run task accepts at most ten source URLs and ten attachments of at most 25 MB each; a fetched page has a 5 MB body cap and 15-second request deadline. Archive imports are limited to 500 entries, 100 MB expanded bytes and four directory levels. After an ambiguous calendar write, the reconciler performs read-only checks after approximately 10 seconds, 1 minute and 5 minutes, then leaves the action unresolved for human review if no matching resource is found; it never sends a second create request automatically. These values are defaults with tests and operator change history, not unconditional claims about every input.

The mobile primary navigation is Chat, Feed, Ideas, Goals and Library; Activity is reachable from a task, notifications and the account menu. The web client has equivalent routes and a persistent activity panel. Empty states distinguish “not connected,” “not configured,” “nothing found” and “source unavailable.” Approval requests use a native trusted sheet or authenticated web page, never rendered agent HTML.
Web routes are /chat, /chat/:thread, /tasks/:task, /feed, /feed/:edition, /ideas, /goals, /goals/:goal, /library, /library/:artifact, /settings/connections, /settings/permissions, /settings/memory, /settings/schedules and /settings/privacy. iOS uses the same resource identifiers and deep-link equivalents. An offline client can stage a text draft locally; only a server commit creates a task or approval. The UI labels a pending request “sending” until the server returns its durable command acknowledgment. Status colors always have text/icons, and approval terms remain readable with large type and a screen reader.
At the first conversational interaction, the UI plainly identifies Kethora as an AI agent. An approval or externally shared report states which authenticated account initiated the action. These transparency choices apply even where a legal exception might otherwise be argued; the exact regulatory obligations and PDF marking implementation are reviewed at G5. An expired approval card explains what expired and offers a one-tap Request approval again action: it reloads current task/policy, renders the same immutable payload if still valid, and requires a new authenticated decision. Any material payload change starts a new approval with new terms. Email and push links only open the trusted signed-in approval route; a reply or notification tap alone cannot approve.
Critical journey J1. On iPhone, the user requests “Compare these three sources, make a PDF, then add the chosen meeting to my calendar after I approve.” The server acknowledges a task ID. It fetches sources, saves source hashes, creates a brief, checks citations and PDF opening, and publishes artifact v1. The user closes the phone. On web they inspect evidence and say “Remove the annual plan.” Task revision 2 marks affected v1 claims stale and removes its current verified label. Artifact v2 becomes current only after new checks pass; v1 remains visible as a stale historical version. The trusted approval card shows the calendar account, title, start/end with time zone, attendees if any, description and stable event identity. After approval the gateway makes exactly that request and verifies the calendar resource; if response is lost, the task enters reconciliation. The user opens the same task and receipt on iPhone.
Critical journey J2. A weekly monitor checks an approved source. A source outage produces coverage_unknown, leaves the last complete baseline intact and records the next retry/notice. When the source recovers, the monitor reports a real diff at most once per occurrence. Pausing the monitor blocks future dispatch even if a late event arrives.
Critical journey J3. A user corrects a saved memory and deletes a source. New model calls use the corrected entry; affected old claims are marked stale. Deletion removes the source from active retrieval immediately, purges derived indexes/previews and any artifact bytes that contain the deleted source unless the user explicitly elects to retain those standalone artifact versions. Retained versions lose their verified label. The receipt names affected artifacts, immediate inaccessibility, active-byte purge deadline, backup expiry and limitations.
4. Architecture and execution boundaries
flowchart TD
  A["iOS and web clients"] --> B["Authenticated API and command service"]
  B --> C["Product database and outbox"]
  C --> D["Durable workflow coordinator"]
  D --> E["Model and context gateway"]
  D --> F["Capability broker"]
  F --> G["Isolated tool and connector gateway"]
  G --> H["Artifact and evidence services"]
  H --> C
The diagram shows control flow, not credential sharing. The model gateway, generated code, browser and retrieved content never hold a database maintenance identity, broker administration route, connector token or production signing key. The workflow engine knows when to resume work; the product database is authoritative for intent, ownership, policy, approval, committed results and user-visible state. An outbox relay awakens workflows after the command transaction commits. Duplicate relay delivery is expected and deduplicated by event ID.
Credential flow: the authenticated account obtains a revocable session, not a provider token in a model prompt. The trusted connection flow binds the selected provider identity and account to a scoped secret reference in the vault. The connector gateway retrieves it for one bound destination and operation; the broker signs a one-effect permit but cannot reveal credentials. A microVM receives no credential reference. A revoked account advances a policy epoch and invalidates unclaimed permits. The G0 credential baseline in §22 records issuer, recipient, storage, lifetime, rotation and revocation for sessions, broker keys, calendar tokens and service identities; implementation adds actual key IDs and paths. Any path from model context, generated code or untrusted browser worker to a credential fails review.
Deployable units. api authenticates and rate-limits; command validates transitions and writes outbox; workflow handles timers/dependencies; model compiles scoped context and validates structured output; broker evaluates policy and issues short-lived permits; gateway owns provider adapters and injects credentials; sandbox runs untrusted code in disposable, egress-restricted microVMs; artifact validates and publishes bytes; evidence verifies acceptance; scheduler creates occurrences; notification delivers committed events; reconciler handles stalled/uncertain effects; operator gives limited, audited incident visibility. Components may share a repository but not privileged runtime identities.
Trust levels. User commands are authenticated intent. Uploaded files, retrieved pages, webhook bodies, tool descriptions and generated code are untrusted data. Model output is a proposal. A broker permit is authorization for one constrained operation. An executor observation is evidence with an observer and coverage. A read-back of an external resource may establish a narrower outcome than the original request. These labels persist in storage and context assembly.
5. Canonical records and database rules
All primary identities are opaque, non-reused UUIDs. Every tenant-owned table has tenant_id, created_at and an appropriate ownership foreign key. Use composite (tenant_id, id) relationships for tenant-owned records, application-level ownership checks and database row security as defense in depth. Runtime roles must not own protected tables or hold bypass privileges. Separate migration and maintenance roles cannot execute agent jobs.

Use database constraints for uniqueness and guarded transition transactions for legality. Cache only reconstructible read models. Sensitive bytes remain in encrypted object storage; event journals contain references and minimum metadata, not raw personal content.
Retrieval ownership: the memory/artifact service owns a PostgreSQL full-text index for G1. G3 can add a vector extension within the same database after its embedding model, version and processor consent are pinned; no separate index service is part of v1. The index key includes tenant, scope, source version, status and sensitivity. A forget/delete transaction tombstones the source and removes searchable rows synchronously; active bytes, cached prompts and previews purge within 24 hours with a receipt line item, retry queue and alert on breach. A source-to-claim-to-artifact edge table drives targeted invalidation; verified unaffected claims survive a task revision.
6. Run state and guarded transitions
received → queued → planning → running → verifying → completed is the normal path. waiting(reason) can follow planning/running/verifying and returns to a validated eligible state when its resume condition is satisfied. paused, needs_reconciliation and cancelling are distinct. Terminals are completed, partial, failed, cancelled and expired. An unresolved consequential effect keeps its invocation in uncertain and the run in needs_reconciliation; the UI must not label it completed or failed.
|Trigger             |Guard and resulting action                                                                                                                                             | |--------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------| |New user instruction|Classify question, task, revision, cancellation, approval, setting or discussion; persist command before acknowledging. Ambiguous external effects await clarification.| |Worker advances step|Match task revision, legal transition, current lease fence, policy epoch and dependency completion; commit state+event+outbox atomically.                              | |User correction     |Increment request revision; invalidate dependent steps and approvals; preserve unaffected evidence; create a successor run if needed.                                  | |Pause               |Stop new dispatch; preserve state and known effects; resume only after live policy/source/budget checks.                                                               | |Cancel              |Commit cancellation barrier; prevent future claims; close pending approvals; report in-flight/confirmed/unknown effects. Compensation is a separate approved action.   | |Worker loss         |Reclaim pre-dispatch step under new fence; reconcile claimed external effects before any repeat.                                                                       | |Complete            |Verify each acceptance criterion from original evidence, publish valid artifact and commit receipt before notifying.                                                   |
At deadline_at, stop new dispatch claims, expire unconsumed permits/approvals, and request cancellation of eligible work. Existing claimed effects enter reconciliation until a confirmed or unresolved outcome is recorded; the provisional receipt itemizes work completed before the deadline, work stopped, and any in-flight effect. A task with an unresolved invocation remains needs_reconciliation and carries deadline_exceeded=true; it becomes terminal expired only after the effect has a recorded confirmed, failed or explicitly unresolved outcome and a final receipt. Explicitly unresolved is a terminal investigation outcome, not proof the provider did nothing; preserve the invocation for later correction. Deadline expiry does not retroactively unsend an action.
Each waiting record has reason, responsible_party, resume_condition, entered_at and optional expires_at. Reasons are approval, input, authentication, provider, device, budget or capacity. A workflow and product projection disagreement triggers reconciliation by event position, never a choice of whichever state looks more successful.
7. API, event and contract shapes
API prefix /v1. All mutations require authenticated owner, a client-generated idempotency key, validated payload and expected_revision where applicable. Return 202 with committed command_id, task_id and event cursor when work continues; return 409 revision_conflict with current revision for stale changes. A 202 means durable acceptance, not successful completion.
Retain accepted command/idempotency keys through the maximum task deadline and external-effect reconciliation interval, with a minimum 30-day retained key/tombstone window. After expiration, a repeated client command is treated as a new request and must pass current ownership, revision, approval and effect-identity guards; it cannot silently replay an old effect. 429 returns {code:"rate_limited", operation, retry_after_seconds, limit_scope, request_id} with Retry-After and non-sensitive per-operation quota headers. Mutation traffic cannot bypass cancellation or revoke operations by flooding a shared quota.

The model gateway uses InferRequest(context_manifest_ref, model_route, output_schema_id, max_units, deadline) and returns InferResult(model_id, output_ref, schema_valid, usage, cost_observation). The adapter must meet a pinned structured-output and cancellation contract, expose actual model identity, redact secrets and fail closed on schema failure. Local tests use deterministic recorded outputs with explicit simulated labels; production configuration supplies the allowed inference endpoint, credential reference and data-processing consent. Model inference never receives a broker secret or directly calls an external connector.
The production route is selected and named in the G0 decision record with a processor DPA and opt-in consent view that explains data categories sent, retention and the route. A timeout or processor outage places the task in waiting(provider) without publishing a draft as final; after recovery, the workflow resumes from committed state. A user may opt into a different route only through a new explicit consent decision; the model cannot silently fall back or quietly deliver a lower-quality substitute.
8. Planning, context and worker execution
Task contract. Admission extracts requested_outcome, artifact_types, authorized_source_scope, required_actions, acceptance_checks, constraints, deadline, budget and missing_decisions. A task with an ambiguous recipient, calendar, amount or destructive target may proceed with independent reads but cannot execute that action. A deterministic planner validates a proposed step graph: all IDs and dependencies exist, the graph is acyclic, the requested capability is registered, the source/destination is in scope, and every step has a timeout, cost reserve and verification method. Invalid plans have at most one schema-repair attempt before a defined wait/failure.
Scoped context manifest. A model receives current task revision, necessary recent messages, goal constraints, confirmed preferences, relevant memories, source snippets with provenance and timestamps, allowed tool schemas, budget and unresolved contradictions. Retrieve only after owner/scope filtering; recheck before returning results. A summary is an index to original evidence, not an authority source. Store exact context and memory revision references for reproducibility. A user-edited personality file may change style and task interpretation; it cannot create grants or alter the broker.
Source ingestion and locators. For each admitted page, fetch with §2 limits and §22 policy, capture original URL, final URL, redirect trail, HTTP status, fetch time, normalized text, original-byte hash, extraction version and coverage state. Start with raw HTTPS fetch; use a locked-down headless renderer only for explicitly permitted sites when raw text is incomplete, with its requests subject to the same egress/robots/rate rules and its mode recorded. A web claim locator contains source version, section/DOM anchor when stable, quote text and quote hash; a PDF locator contains file hash, page and text range or bounding box; a user text file has line/offset and hash. A locator test resolves against retained source bytes/text and returns unresolvable when extraction changed. Insufficient extraction produces coverage_unknown and cannot silently pass a factual-support check.
Delegation. A child worker receives parent run/revision, bounded objective, selected source IDs, strict subset of permits, own workspace branch, reserved portion of shared budget, deadline and output schema. It returns claims, evidence candidates, artifact references and limitations. Initial maximum is two children and one delegation level. Parent accepts results only if task revision and evidence remain current. A second model’s agreement is a review, not independent confirmation of an external effect.
Turn accounting: every inference call, including child calls, schema-repair calls and claim-support judgment calls, counts against the parent task’s twelve-turn limit and shared cost ceiling. The judging call may batch multiple claims under one task/source scope; it still records one judgment per claim and cannot receive additional, unapproved source data. A substantive replan increments the replan counter when it changes dependencies, capabilities or acceptance work; retrying the same failed call cannot evade the cap. The client displays turns used, reserved cost and estimated remaining budget. Verification and reconciliation of an already claimed consequential effect have a separate upfront reserve and continue even if the task’s ordinary work budget is exhausted.
Retry classes. Safe reads: at most three attempts with bounded exponential backoff, respecting retry hints and the task deadline. Model schema repair: one attempt. Uncertain external write: no automatic resend unless the adapter’s tested idempotency contract covers the same logical effect and unchanged payload; otherwise reconcile and expose unresolved state. Repairs require a changed input or recorded failure reason. No loop may exceed time, cost and step count limits.
9. Broker, grants and approved external effects
The broker holds a versioned operation registry. Each operation declares account/resource binding, purpose, data category sent to another processor, destination, semantic side effects, reversibility, credential scope, risk class, verification and reconciliation. HTTP method alone never determines whether an operation is read-only. The broker uses the same semantic classification for connector, browser and generated application routes.
Policy precedence: authenticate service and user → verify tenant, account and resource → enforce hard restrictions → reject cancellation, revocation and stale task revision → enforce source/destination/data scope → apply explicit deny → match a valid narrow grant or exact approval → reserve remaining budget/capacity → issue a one-effect permit. Missing/failed authoritative policy lookup denies dispatch. Permits carry tenant_id, task_id, run_id, step_id, effect_key, payload_digest, operation, account_id, destination, scope, policy_revision, revocation_epoch, fence, issued_at, expires_at and signature. The gateway independently verifies all fields and checks revocation again immediately before claiming dispatch. A permit cannot be edited by the worker.
Default classes: authorized public/source reads may run within the accepted task scope; private account reads require an account-specific grant; external writes, shares, publication, deletion, financial commitments and credential use require explicit narrowly bounded grants or exact-action approval. In this release, purchases and arbitrary unreviewed integrations are hard-denied. Users see an effective-permission explanation, can revoke active grants, and can distinguish changing a default from stopping an already-dispatched effect.
Approval card. Render from an immutable stored payload: account, exact calendar, title, start/end with time zone, description, attendees, data being sent, expiration and artifact link when relevant. If attendees are included, the card says the calendar service may send invitations or updates to those people. The approval decision binds to the payload digest and effect key. A material edit creates a new payload version and invalidates approval. One approval can cover safe transport retries of the same effect only when the adapter’s tested contract allows them; it never authorizes a new event. An expired card offers the trusted re-request flow in §3.
Atomic claim boundary. In one product-database transaction, lock the invocation, verify task revision, unconsumed approval, live policy epoch, fence, cancellation, budget reserve and unique effect key; mark dispatching and record the claim time. The provider call happens outside the transaction. Cancellation committed before claim wins. Once claim commits, an in-flight network call may still complete; record that limit in the receipt. After call, persist provider observation and settle cost, then verify acceptance separately.
Policy rollout: a new policy version is validated against fixtures and canaried on read-only or synthetic accounts before dispatch use. Revocation or a restrictive policy change increments the affected epoch and invalidates every permit not yet claimed; an already claimed provider call may still complete and must be reconciled. A loosening policy never grants an existing task additional access: obtain fresh user authorization where required. Record old/new versions, rollout cohort, operator, time and result; rollback does not restore a revoked grant.
10. First connector and uncertain-effect reconciliation
The gateway exposes a narrow versioned CalendarAdapter contract: listCalendars, probeCapabilities, prepareOneOffEvent, create, readByStableKey, reconcile and disconnect. The broker authorizes a semantic one-off event creation for one provider account and calendar, not arbitrary adapter HTTP. The connection record binds issuer, provider account, calendar ID, host where applicable, server class, credential reference, tested capabilities and probe timestamp. Store secrets in the vault. Never pass a password, access token, session cookie or raw credential to a prompt, agent file, untrusted code or ordinary application log. Status distinguishes writable_tested, read_only, insufficient_scope, expired, revoked, temporarily_unavailable and unsupported, per account and server class; stale capability evidence blocks a write until rechecked.

Reconciliation: the atomic dispatch claim creates one logical effect key and a provider-specific stable identity. Record invocation, immutable payload, request attempt, response or timeout, observer, read-back attempts and final result as separate events. On ambiguity, scheduled read-only checks follow the bounded §2 intervals; inaccessibility, conflicting resource or absent proof ends in needs_reconciliation with an operator/user-visible receipt. Do not silently assume failure and re-create. Verification/reconciliation capacity remains available even after ordinary task budget exhaustion or deadline. Provider throttling obeys Retry-After for reads; it never justifies a duplicate write. Any later compensating deletion is a fresh approved operation.
Each adapter validates the exact OAuth redirect origin or CalDAV endpoint, TLS, issuer, host allow-list and actual egress against private-network and metadata addresses. Credentials reach only the bound provider destination; do not send them to redirects or a user-supplied server pretending to be that provider. Webhooks, if added, enter a signed/deduplicated inbox; a webhook is evidence of a provider event, never a new user instruction. Connector removal blocks new dispatch, advances its policy epoch and records treatment of retained data and in-flight effects.
11. Sandboxes, browser and generated artifacts
Untrusted generated code runs in a disposable microVM with a non-root identity, read-only base image, no host mounts, no broker or credential route, disabled metadata access, strict CPU/memory/process/wall-time limits and denied network by default. Inputs are staged copies; outputs are uploaded through the artifact staging API and validated before publication. Images and dependencies are pinned and scanned. Installing arbitrary packages is disabled in the first release; reviewed dependency bundles are introduced only with a new fixture and supply-chain gate.
A browser worker has a separate session and an operation vocabulary: navigate to an allowed host, inspect a permitted page, interact with referenced elements, upload a named approved file and submit an exact approved action. Its control protocol, cookie storage and credential filling remain outside generated code. Validate first URL, redirects, subresource destinations and outbound network; treat screenshot, clipboard, upload and download as data movement. If a semantic write cannot be mediated reliably, present a human takeover instead of automating it. Takeover increments the controller generation and invalidates agent element references. A paused/stale agent cannot resume concurrent input.
Executable artifact previews use a distinct origin without product cookies; all data access and writes use brokered capabilities. Creation or preview of a generated application does not grant it connector access. Release a generated application capability only after isolation, origin, egress and approval-path tests pass. Media uploads and previews must pass type, codec, duration/resolution where applicable, malware and access-control checks.
12. Memory, system files and artifact lifecycle
Persistence classes: conversation is what was said; task/run state is what happened and remains to do; personal memory stores confirmed facts/preferences with provenance; policy states what is authorized. They never substitute for one another. A memory record has owner, scope (task or profile), source, observed_at, valid_until?, sensitivity, status, revision and content reference. Explicit user edits promote immediately after validation; model-inferred profile memories appear as candidates and require confirmation. A contradiction blocks automatic promotion. Sensitive third-party information is not saved as a reusable personal preference simply because it appeared in a source.
Controlled editable files expose identity, preferences, tools available to the assistant and a human-readable memory view. Bind meaning through a database type and stable file ID, not a filename. A save requires expected revision, size/type validation, history and a change event; conflicting edits show a diff/merge decision. No file text can change security policy, connector scopes, worker privileges or approval rules. Imported archives are quarantined against decompression bombs, file count/size limits, traversal, symlinks and executable instructions.
Artifact publication: allocate staging slot → upload/generate bytes → validate owner, hash, size and actual type → run format-specific checks → render/open supported views → commit manifest and current pointer in one guarded transition → expose in Library. PDF briefs must parse, render, contain expected sections and carry a tagged reading order, structured headings and alt text for meaningful figures; the produced PDF must pass a PDF/UA conformance checker for its declared PDF/UA profile plus a human screen-reader check on representative output. Choose and lock the precise conformance profile with the generator in G0. A visible AI-origin label, structured PDF metadata and a signed manifest containing generator identity, output hash and provenance make generation detectable; the legal workstream decides whether the shipped format meets any applicable machine-readable marking rule. Metadata alone is not presumed legally sufficient. Markdown has checked links/citations; CSV has expected schema and row count; images/media must decode and be viewable. A partial or invalid file remains a labeled draft, never a completed deliverable. Revision retains prior versions and exact source relationships. Sharing/export is a separate user-authorized operation that checks access again at download time.
Evidence manifest and support judgment: split each brief into atomic, material factual claims with stable claim IDs. For each, record source object/version/hash, exact locator and excerpt, retrieval time, extraction status, extraction coverage, claim-to-source edge, judgment (supported, inference, disputed, missing), rationale, judging route/model ID/prompt version, confidence if calibrated, run/revision and reviewer override history. Deterministic checks resolve the locator against retained source bytes and ensure the claim is current; a separate, budgeted different-model review call receives only the claim and cited original excerpt, judges whether that excerpt supports the exact wording, and emits a schema-validated judgment event. Detect competing source assertions and label unresolved contradictions disputed. Its verdict is fallible: calibrate against human adjudication, sample release output, and send ambiguous or disputed material claims to user-visible human review or remove/reword them. A reviewer cannot approve a broken locator. Every source-verified factual-brief label must trace to current support events for every material claim; inference, disputed, missing or stale claims cannot be quietly reported as verified. Source verification establishes faithful attribution, not independent truth of the underlying sources. A claim-to-source-version-to-artifact-version lineage index marks affected claims stale on a corrected or deleted source while preserving independent evidence. Deleting a source tombstones dependent artifact versions containing its content and disables their share links immediately, then purges active bytes within 24 hours unless the user separately confirms retaining a standalone artifact; retained versions cannot keep a verified label grounded on deleted evidence. Publish the actual support state and source coverage in the receipt.
Model-quality gate: build a versioned golden set of at least 50 independently annotated tasks across faithful synthesis, conflicting sources, misleading citations, omissions, corrections, absent sources and hallucination traps. Lock train/dev/held-out splits and annotator rubric before using the held-out portion for release; do not tune against its hidden labels. Evaluate the brief against user intent and source coverage, claim support, citation correctness and false verification separately. On the held-out set require zero fabricated source locators, zero false verified-completion labels, at least 90% agreement with adjudicated human support labels on material claims, ≥0.80 macro-F1 across the four support labels with at least ten adjudicated examples of each label, and at least 80% of briefs rated ≥4/5 for task fulfillment without a material omission by two independent human reviewers. Later changes may not lower that usefulness rate by more than two percentage points relative to the last accepted route on the same frozen set. These are finite release baselines, not a proof of perfect accuracy; report counts/denominators, per-class results and uncertainty bounds, and inspect every severe disagreement. Re-run E01–E03 whenever model, route, prompt, judge rubric, source extraction or context assembly changes; failures block the verified label and route rollout. Receipt-level user feedback and correction rate supply new reviewed cases, not silent changes to the held-out set.
13. Goals, schedules, Feed and Ideas
A Goal stores desired outcome, owner, milestone IDs and explicit task/monitor links. A Task is bounded work; a Monitor evaluates a condition repeatedly; a FeedEdition presents selected information; an Idea proposes possible work. None silently creates another class of object without an explicit rule and user-visible event.
Monitor contract: source scope, predicate revision, time zone, trigger, overlap mode, missed-run mode, baseline reference, freshness limit, authority expiry, cost ceiling and notification policy. Scheduler identity is (monitor_id, schedule_revision, intended_occurrence). Default missed-run policy coalesces multiple obsolete read checks into one current check; default overlap skips a new occurrence while one is running and records the skip. A successful complete observation updates the baseline. Results are changed, unchanged or coverage_unknown, with coverage and source hashes. A failed read cannot become unchanged.
For a local scheduled time skipped by a daylight-saving transition, run at the first valid local instant after the gap. For a repeated local time, run once at the earlier offset. Persist intended local time, chosen UTC instant and zone identifier in the occurrence record; changing the user’s time zone creates a new schedule revision and does not rewrite completed occurrences. A recurrence with an external write requires a separate grant defining maximum frequency, exact account/action bounds and expiry; the read-only monitor grant does not imply it. Give notice at least seven days before write authority expires; renewal requires a fresh, authenticated grant with displayed scope. If authority expires, the monitor may perform separately authorized reads but pauses proposed writes, records the reason and never auto-renews.
Feed: version user instructions; fetch only permitted sources; retain publication and retrieval dates; deduplicate; check factual support; create a stored edition with partial/complete coverage before notifying. Apply a per-edition cost ceiling and a shared daily background budget across editions/Ideas; reserve model and support-check calls before starting. If either ceiling binds, mark the edition partial_budget with omitted-source/card count and next eligible refresh, and show this in the client. Reactions change future ranking only under a documented preference policy. A discussion links to the exact card and source set. Editing instructions affects future editions unless the user explicitly requests regeneration. A failed source does not get replaced by an invented story.
Ideas: store title, proposed task, evidence, expected benefit, access needed, cost estimate/unknowns and expiration. On acceptance, recheck freshness and admit a task through the same broker and budget process. Dismissal reduces repetition; opening an idea never executes it. Background generation has its own quota and cannot create an infinite chain of new background tasks.
14. Evidence, receipts and privacy
Each task criterion has a named verifier and admissible evidence before execution. The evidence service compares requested action, broker decision, stored payload, gateway dispatch and external observation. An executor can report an observation; it cannot mark its own claim independently verified. For a saved document, require committed bytes, readable format and the relevant content/citation checks. For a calendar change, require matching resource and agreed fields. For “no change,” require complete successful source coverage. For an alert, distinguish queued, provider accepted and device displayed when only some are observed.
The task receipt contains request revision, start/end, completed criteria, artifact versions and hashes, consequential operations and provider references, evidence check results, coverage, actual and provisional cost, known uncertainty, remaining monitor status and links to activity. It offers optional one-tap “Was this right?” feedback and correction links. Record feedback by task class and route; a product-quality dashboard shows eligible tasks, completed/verified/partial/unresolved counts, user-reported usefulness, correction rate, citation-support failure rate and judge disagreement, with cohort and denominator. Tamper-evident signing uses a service-held key separate from executors; a signature proves receipt integrity and issuer under its trust assumptions, not that a claim is factually correct.
Data handling defaults: personal messages, files, memory and task evidence remain until the user removes them or resets the account. Transient source fetches not linked to a retained artifact age out after 30 days; sources supporting a retained artifact remain until that artifact/source is deleted or its retention setting expires. Raw prompt/response diagnostics are off by default; minimal operational request metadata is retained 14 days, restricted security events 90 days, and backups for a rolling 30 days. Optional per-task diagnostic capture needs affirmative consent, can be excluded for any task, samples no more than 5% of otherwise eligible tasks, expires after 30 days, excludes credentials and access tokens, and logs every support access. Deletion tombstones remain active at least 35 days and longer than the oldest restorable backup plus a tested safety margin; backup restore replays tombstones and deletion generations before any account is activated. Every processor receives only scoped data needed for the task; processor choice and export of private input require account consent and an enforceable no-training-use commitment for user content. No user content is added to model training by this product’s own pipeline or authorized processors.
Export/reset: export produces a versioned manifest with object IDs, relationships, hashes, formats and omissions. Its integrity is checked before delivery; the v1 format is not importable into a new account and offers no restore feature. User-uploaded archive import is a separate quarantined attachment path. Reset first increments the assistant/account generation, blocks new commands, revokes grants, cancels schedules, and accounts for in-flight effects. It then deletes active objects, indexes, summaries, previews and staged content. A restored snapshot or late webhook checks deletion generations before creating data or resuming a run. The receipt says what was deleted now, what is pending backup expiry, and which external copies lie outside the product’s control. Support access requires an explicit role, limited duration, audit trail and documented incident procedure.
Notifications: a committed event creates one notification intent per recipient/channel in a transactional outbox with a deterministic intent key. Retries preserve that key and record queued, provider_accepted, delivery_failed and device_displayed only when a client acknowledgment is available. Provider acceptance is not proof of inbox placement or reading. The in-product inbox deduplicates by intent ID; email and push use provider idempotency where available and tolerate uncertain third-party delivery by disclosing status rather than minting a second distinct alert. A duplicate scheduler wake cannot create a second user-visible intent.
15. Security, identity and abuse boundaries
Registration creates an account, a passkey binding and an assistant identity, then offers one-time recovery codes. Invites for the first cohort are single-use and expire; iOS App Attest on supported devices is defense in depth, with an accessible verified-account fallback if attestation is unavailable. Web uses secure, HttpOnly, same-site session cookies and CSRF protection for mutations; its approval page is on a trusted origin isolated from generated HTML or application previews. iOS stores a device-bound refresh credential in the Keychain under an after-first-unlock, this-device-only accessibility class and stores cached sensitive artifacts under complete-until-first-unlock file protection, upgrading to complete protection for files unnecessary in background; document background access exceptions per file. iOS push uses token-based provider authentication and never conveys approval authority. Rotate sessions after recovery or high-risk changes. Approvals for external write, connection creation, credential change, export and reset require a recent authenticated step-up and display the exact account/action. A device notification, email reply or free-text “yes” cannot serve as authorization.
Recovery ceremony: a lost-passkey user presents an unused one-time recovery code and completes a challenge to the previously verified email. Consume the code atomically, revoke all other sessions and provider grants, rotate the current device session and require passkey re-enrollment. Begin a 24-hour risk hold on new external writes, destructive reset and data export; show its end time. An already enrolled independent passkey may perform fresh step-up to end the hold earlier, subject to risk checks. Without code plus verified-email challenge, recovery does not activate an account; support cannot override it alone. Re-enrollment and hold transitions enter the security activity log, and notifications go to existing verified channels.
Rate-limit by account, device, IP risk and operation; apply queue fairness so one expensive background task cannot starve an interactive cancellation. File and network ingestion have byte/time limits, malware checks and content-type verification. External URL access rejects loopback, link-local, private and metadata networks, including DNS rebinding and redirects at actual egress. Never use user-supplied hostnames as unrestricted server-side requests. Unknown external operations are disabled until their metadata, permission and reconciliation behavior are reviewed.
Service credentials are per environment and least-privilege. Encrypt at rest and in transit; key rotation, account disconnect and incident revocation have tested runbooks. Backup encryption keys and production broker signing keys are outside agent execution and development environments. A signed permit is still checked against current revocation epoch, resource identity and fence. A privileged maintainer may bypass ordinary row-level checks, so the agent/runtime and normal support identities cannot hold that role.
Threat regression set: hostile text in a retrieved page tries to change instructions; an imported ZIP includes traversal and executable prompts; sandbox code probes secret and metadata endpoints; a generated preview requests privileged API access; a stale browser controller submits after takeover; a user guesses another tenant’s IDs; a restored backup revives deleted data; a changed approval payload replays; denial through one adapter is retried through another; a compromised model processor returns malicious structured output; a forged provider endpoint solicits credentials; and an email link tries to approve without authentication. Each scenario has an expected blocked state and retained minimal evidence. Structured model output is schema-validated and allowed actions are rechecked against the operation registry before dispatch.
16. Operations, capacity and observability
Production uses two API, broker and connector-gateway replicas across two availability zones; a primary/standby database, durable workflow store, versioned object storage, redundant outbox relay, and separately scaled read, artifact and sandbox workers. One US East region is authoritative for writes; the second zone covers a zone failure when dependency health permits, not a whole-region failure. Region disaster recovery uses encrypted backup restore with a target under four hours and at most a 15-minute backup gap, followed by write-disabled reconciliation of provider effects and database/outbox positions before dispatch resumes. Health checks report readiness only after dependencies needed for safe dispatch are available; a broker outage fails closed for new effects. Development uses local containers and deterministic fake integrations; staging has separate identity, secrets and synthetic accounts. No development or staging token can reach production data.
Initial SLO hypotheses under declared 100-account/20-active-job staging load: command durable acknowledgment p95 <2 s excluding upload transfer; reconnect-to-authoritative-view p95 <5 s; healthy scheduled occurrence begins p95 <60 s after due time; eligible work recovery after worker loss <90 s; revocation blocks every claim committed after its transaction; backup restoration target <4 h with ≤15 min backup gap, followed by write-disabled reconciliation. These are test targets, not guarantees. Load tests must state cohort, region, dependency health and excluded network faults before results are published.
The web release target is WCAG 2.2 AA assessed across the whole supported journey, including error, approval, waiting and recovery states; the iOS release target includes full screen-reader navigation, Dynamic Type, reduced motion, sufficient contrast and hardware-keyboard operation where controls are present. A checklist alone is insufficient: include automated checks and human assistive-technology runs on both supported clients in the release receipt.
Trace IDs propagate through task, run, step, invocation, provider adapter and artifact checks. Metrics include queue age, stuck waits, uncertain invocations, missing verification, permission denials, source coverage, notification duplicates, model/tool usage and budget reserves versus settled cost. Traces are diagnostic data, not business evidence. Raw prompts and credentials are not routine telemetry. Operator dashboards show affected account, safe state, blocked next action and reconciler status. A dead-letter event can be redriven only after checking current revision, policy, budget and effect identity.
For incidents, freeze the affected dispatch class, preserve access-controlled evidence, revoke implicated credentials, reconcile effects, notify affected users of known impact, ship a verified fix and resume narrowly. Before G2, name the primary incident owner, backup and response schedule; drill the wrong-external-action scenario in staging and record outcome. Break-glass access needs two authorized people, a documented incident, fixed expiry and full audit, and cannot secretly retroactively approve an agent action. Practice restore with a provider action after the backup point; the product must not resend it after restoration.
Cost ledger: reserve before each model, tool, sandbox, rendering or connector charge; settle against measured usage; release unused reserve only after a confirmed safe outcome. At a consequential-effect claim, reserve a bounded verification/read-back and reconciliation allowance in a separate safety pool. Once dispatch is claimed, continue necessary verification/reconciliation even if the ordinary task ceiling is exhausted or the deadline passes; log the exception and alert an operator if the safety pool itself is exhausted. Stop only new work at the task ceiling, preserve a checkpoint and show the next user choice. Parallel workers share one parent ceiling. Track all attempts, failures, verification, storage, egress and support time. Product entitlement, internal task budget and any later external purchase authority use separate records. Never silently increase task work spend because a model predicts success.

19. Repository, reproducible build and deployment handoff
Create one repository with these stable directories and ownership: apps/web, apps/ios, services/api, services/command, services/workflow, services/model, services/broker, services/gateway, services/artifact, services/evidence, services/scheduler, services/notification, services/reconciler, workers/sandbox, packages/contracts, db/migrations, tests/unit, tests/contract, tests/fault, tests/e2e, tests/evals, docs/coverage, docs/decisions, docs/runbooks, infra. Generate typed client/server contracts from a versioned API schema. Keep policy schema and operation registry under reviewed code; editable user content never compiles into them. The G0 handoff includes a typed CalendarAdapter seam, claim-support judgment schema and executable source/citation fixture pack.
The clean-checkout contract is: install the pinned toolchains; start local database, workflow engine, object store and test calendar fixture from checked-in container definitions; apply migrations; load synthetic fixture accounts; start API/workers/web; run unit, contract, fault and web end-to-end tests; build the iOS client with documented signing placeholders; run the iOS test target in simulator; export the test receipt. A setup script validates environment variables without printing secrets. Provide example config, locked packages, pinned images, SQL migrations, safe rollback/forward-fix guidance, generated API spec, non-sensitive test fixtures, feature manifest and a troubleshooting guide.
Staging deployment applies migrations before canary rollout and exercises task versions waiting on approval, running monitors and uncertain effects. Use Temporal Worker Deployment Versioning with pinned task workflows; keep old worker deployments alive until their runs drain or cross a tested Continue-as-New boundary. Longer-lived monitors use Continue-as-New with an explicit upgrade boundary and carry product IDs only; policy and approvals are re-read from the authoritative database. G0 records the exact server and TypeScript SDK versions, upgrade strategy and minimum compatibility; the N→N+1 fault test starts an approval wait on N, deploys N+1, approves and verifies correct resume, then repeats during an uncertain effect. Rollback may restore code but cannot roll back an already accepted external action. Production release signs images, restricts service accounts, applies network policy, checks backups and alerts, rolls out a canary, verifies acceptance smoke tests and records the exact feature manifest. Secret values are provisioned through a protected secret service and never committed.

The initial cohort limit is 100 invited accounts. External writes stay off by default for an account until that specific connection passes capability testing and the user grants the operation. Features beyond the tested matrix are labeled unavailable and hidden from unsupported action paths. Expand formats, channels and connectors one at a time with their own operation metadata and evidence tests.
G5 outcome measure: over at least 14 consecutive invited-alpha days, with at least 50 eligible admitted read-to-brief tasks from at least 25 distinct accounts, require ≥95% verified-success by the user-agreed deadline and zero hard blockers. Eligible is fixed at admission: supported input types, source URLs and attachments pass admission validation, request within documented size/cost bounds, consented model route and sufficient time for the declared SLA. A source that later proves inaccessible remains in the denominator and yields partial/failed work rather than a retrospective exclusion. Denied, cancelled, timed out, partial and unresolved tasks remain visible as separate counts; do not exclude a failure after admission to improve the denominator. A user who cancels before any work begins is excluded by a predeclared rule, with its count shown. The verified-success numerator includes only tasks whose PDF opens and whose required material claims have current support events; a reported completed without evidence is a hard blocker even if the percentage passes. Report actual tasks, route, support mix, correction rate, costs, unknown effects and statistical uncertainty; the gate fails if sample size is missed.
21. Definition of the built product
The product is build-complete for its declared release only when a user can delegate a real task, interrupt it, close the iPhone client, reopen it on the web, inspect truthful progress, correct the work, approve a precisely shown consequential action, receive a provider-backed or honestly unresolved outcome, and retrieve an actual validated artifact and receipt. Editable memory, controlled files, Goals, monitoring, Feed, Ideas, permissions, export and reset must operate against the same persistent backend on their declared platforms. Every shipped promise has an acceptance result and a reproducible source/build record; every unsupported integration is stated as unavailable.
The next action is G0: create the repository, migrations, typed command/event contracts, operation registry, synthetic fixtures and executable invariant tests, while completing the processor/consent and workflow-version decisions in §22. The contract work can begin immediately. No private production data enters the system until the model route and processor terms are named; no external write ships until a tested account class, owner and response runbook are ready. The resulting G0 receipt states which decisions were fixed, which remain as gate blockers, and the exact evidence that closes them.
