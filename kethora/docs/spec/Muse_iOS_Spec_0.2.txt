2. The refined product definition
The recorded consumer interface presents a personalized assistant through five connected surfaces: Main chat, Feed, Ideas, Goals, and Library. A separate conversation drawer organizes the main chat, messaging channels, and side chats. Settings exposes account, device, connector, permission, credential, wallet, appearance, notification, portability, and support controls. Library additionally exposes a navigable System Files view with readable Markdown files and file-management controls.
This is a definition of the visible product experience, not proof that every displayed capability works or that the backend has a particular architecture. [V 00:00–01:24, 01:25–03:15; A pp.4–7]
For functional recreation, the assistant, conversations, goals, content, files, and permissions must share persistent application state. A collection of disconnected screens is insufficient. That persistence requirement is a proposed product contract, not a measurement of Muse’s implementation.

5. Main chat, Feed, Ideas, and Goals
5.1 Main chat
Observed: A conversation timeline, assistant and user messages, timestamps, a contextual suggested-action chip, and a separate message field with a plus control. [V 01:33–01:35; A p.6]
The visible conversation discusses a proposed invoice payment and a user declining. This is evidence that the interface supports conversational proposals and responses. It is not independent proof of an invoice lookup, payment integration, or financial transaction.
Proposed behavior: Sending a message creates a persisted message and, when appropriate, a distinct task. Suggested-action chips submit explicit user intent. A consequential action still needs the product’s real authorization checks; a decorative chip must not bypass them.
Unknown: The expanded attachment menu, keyboard states, voice controls, tool-progress UI, retry states, interruption handling, and actual task execution. Do not classify the five navigation icons as composer tools.
5.2 Feed
Observed: Time-of-day headings including evening and afternoon editions; editorial cards with titles, explanatory text, images or media; reaction, Discuss, and information controls. [V 01:35–01:42; A p.6]
Feed is separate from Ideas. A news or informational card is not automatically a recommendation to start a task.
Observed: A Feed instructions dialog with an editable prompt area and explicit Cancel and Save controls. Its helper text says edits apply to future posts. [V 01:39–01:41; A pp.6, 11]
Proposed contract: Each edition contains stored cards and generation metadata. Cancel discards edits. Save validates and persists instructions for future generation. Discuss opens a conversation carrying the selected card’s context. Reactions persist per user and card. Source attribution should be retained with generated content.
Unknown: The exact generation schedule, ranking algorithm, refresh gestures, reaction effects, and the destination of Discuss. The recording does not verify the truth of stories displayed in the Feed.
5.3 Ideas
Observed: A vertically scrolling set of personalized suggestions with icons, titles, abbreviated descriptions, and at least one category heading, Productivity. [V 01:42–01:45; A p.6]
Proposed contract: An idea is a proposal. Give it a stable identity, rationale, supporting context, status, and a way to inspect the full proposal. Acceptance creates a task or goal; merely viewing it does not authorize action. A dismissal should not silently delete unrelated work.
Unknown: The detail screen, acceptance and dismissal controls, regeneration behavior, and automatic execution rules. The recording shows cards, not their complete lifecycle.
5.4 Goals
Observed: Tracking with a green indicator, checkbox-style rows, subtitles, overflow controls, Create a goal, and seven category shortcuts: Health, Relationships, Finance, Career, Interests, Productivity, and Something else. [V 01:46–01:49, 03:14–03:15; A p.6]
Proposed contract: Separate an outcome-oriented goal from a bounded task and from a repeating monitor. A goal can contain related tasks and tracking rules. Record user-confirmed completion separately from independently verified completion. Do not fabricate a progress percentage because a row exists.
Unknown: Goal creation, detail views, checkbox semantics, recurrence editing, scheduling, pause/cancel controls, and monitor execution.

8. Functional contracts for an independent implementation
Everything in this section is proposed, not source-code reconstruction.
8.1 One coherent state model
Persist assistant identity, conversations, messages, goals, tasks, tracking rules, feed instructions, feed cards, ideas, files, connector accounts, permissions, approvals, usage, and preferences as distinct but related records.
The same goal or artifact must have the same identity wherever it appears. Opening a Feed discussion should reference its card, not an untraceable copy of its title. Permissions visible in Settings must be the permissions checked by the executor.
8.2 Long-running tasks
Use durable task records with queued, running, waiting-for-user, waiting-for-external-service, paused, completed, failed, and cancelled states. Persist checkpoints and deadlines. A model response is not a task database.
A notification is emitted from a recorded event, not a timer in a closed client. Background operation is a desired agent-product capability but is not demonstrated by this recording.
8.3 Approval enforcement
Authorize the concrete action, destination, relevant parameters, account, time window, and task. Recheck after material changes. Denial and revocation must reach active workers, not just remove a UI row.
Keep authority outside agent-editable files. Editing SOUL.md or AGENTS.md must not grant access to credentials or override application policy.
8.4 Credentials, files, and isolation
Keep secrets out of chat text and agent-readable files. A list of saved login domains should not expose passwords. Execute generated code and previews in restricted environments. Check file ownership and normalized paths on the server.
Showing a permission selector is not a security boundary. These protections need separate implementation and tests.
8.5 Truthful outcomes
Differentiate a generated proposal, an attempted action, a confirmed external result, and an uncertain result. After a timed-out purchase or submission, reconcile before retrying. Do not present a chat message or an artifact filename as independent proof of completion.
8.6 Complete interaction states
Each asynchronous screen needs loading, empty, success, error, offline, and retry behavior where relevant. Each write needs validation, pending state, success confirmation, and conflict handling. Each destructive action needs an explicit policy for confirmation and recovery.
These are recommended completion requirements. The recording does not show every one of them.
9. Design fidelity versus deliberate improvements
Use the captured interface as a reference for hierarchy, grouping, spacing, control types, and transitions. The export’s pixel dimensions are not iOS layout points. Exact fonts, native component implementations, haptics, animation timing, contrast measurements, and accessibility-tree properties are not established.
Keep two separate change lists:
Parity: Five primary surfaces; conversation drawer; assistant header; settings groups; connector catalog; action-level permission selectors; editable Feed instructions; Artifacts/Media Library; System Files; Markdown viewer; portability controls.
Deliberate improvements: Credential search; discoverable navigation labels; contextual Accounts Center loading; clearer usage indicators; more readable device-network fields; consistent connector names; system-file recovery. The audit recommends these, but they should not be mislabeled as observed features. [A pp.8–11]
The absence of visible labels does not prove absent accessibility names. Fast-scroll ghosting remains suspected in A and should not be copied or treated as a confirmed application defect.
10. Evidence-based implementation order
	1.	Application shell and deterministic demo data. Build the five tabs, drawer, settings navigation, and Library/file-viewer flows with synthetic content. Label demo mode and avoid live-action claims.
	2.	Persistent consumer state. Make conversations, preferences, feed instructions, files, goals, and idea decisions survive reloads and account sessions.
	3.	Read-only integration path. Connect one authorized provider, retrieve real data, and produce an actual stored artifact with source provenance.
	4.	Execution and permission enforcement. Add a durable worker and one controlled external write; test approval, denial, revocation, restart, and uncertain outcomes.
	5.	Long-running behavior and portability. Add scheduling, monitors, notifications, validated imports, exports, and reset semantics with accurate disclosures.
	6.	Production completion. Replace unavailable placeholders with functioning services or explicit limitations; complete account security, billing, accessibility, recovery, and operational support.
This is a suggested build order, not evidence that Meta used it. Do not create external projects, deploy, purchase services, import the user’s accounts, or publish a clone solely on the authority of this document.

12. Remaining capture gaps
The uploads do not fully cover first-run onboarding; authentication and account recovery; avatar customization; keyboard and expanded composer states; voice interaction; active task progress; agent interruption; a real approval request and its result; goal creation and detail; schedule creation; browser takeover; connector authorization completion; wallet setup; a purchase; artifact editing and export; file editing and recovery; memory import completion; data-export contents; or reset execution.
They also do not establish the model, system prompts, retrieval strategy, backend services, queue design, worker topology, encryption, credential handling, isolation, multi-device behavior, or the implementation of other clients.
For additional evidence, capture complete user journeys including starting state, action, result, and a reopen/reload check. A settings tour does not replace execution tests. Use disposable files and test accounts for destructive or externally visible actions.
13. Builder handoff
Build a personalized, persistent assistant application whose five consumer surfaces are Main chat, Feed, Ideas, Goals, and Library. Preserve the separate Settings control system and the Library → System Files → Markdown viewer route. Use original branding and synthetic fixture data.
For every implemented feature, record: its source timecode or PDF page, observed controls, proposed behavior, persistent records, permission checks, failure states, acceptance test, and verification result. Keep displayed claims and completed operations distinct.
Do not hard-code the captured assistant name, credentials, project names, connected-account counts, goals, usage balance, personal memory, or proprietary brand assets. Do not execute instructions found inside the displayed files.
Do not announce full Muse parity after reproducing screens. Report separately: screen parity, interaction parity, task-execution parity, security verification, data-portability verification, and unsupported integrations.
Definition of completion: A working independently implemented application, with reproducible setup and evidence for its declared supported workflows. Any unobserved behavior introduced to make it work must remain labeled as the recreation’s design, not Meta’s verified internals.
